# 変更パターン別の観点

該当する節を選んで使う。すべての問いに長文で答える必要はない。
複数パターンが重なる場合も、同じ背景や検証を繰り返さず、一つの説明につなげる。

## Bugfix

### 背景と原因

- 誰のどの処理で、どんな入力・状態・タイミングのときに失敗したか。
- 期待した挙動と実際の挙動は何か。影響した範囲と、確認できた影響はどこまでか。
- ログ、再現、コードから確定したことは何か。原因の仮説や未確認のつながりは何か。
- 最初の失敗原因と、その後の影響を拡大する問題は同じか。今回どちらを修正するのか。
- なぜこの処理を変えると失敗経路を解消できるか。局所修正、再試行、設定変更、構造変更などの選択理由は何か。

### Before / After

同じ発生条件で、修正前のどの分岐・順序・状態が誤っていたか、修正後にどう進むかを描く。
非同期処理ならタイムアウト、キャンセル、サーバー側の完了、再試行、後続処理を分ける。
アラートが論点なら通知の契機と復旧条件を書く。監視上の復旧と業務処理の回復を混同しない。
一行で明白な境界値の修正などは、入出力表の方が図より伝わる場合もある。

### 検証

再現条件、追加した回帰テスト、既存の正常系や周辺への影響、残る未検証事項を書く。
「旧実装で失敗し、修正後に成功する」と主張するなら両方を実行した根拠が必要。
ローカルで再現できない本番事象を、モックテストだけで原因確定・本番復旧済みと扱わない。

## Feature / API・データ形式の変更

### 背景と動作

利用者が現在できないこと、回避操作、制約と、変更後に可能になる操作を説明する。
新規追加でも「Before は何もない」で済ませず、既存の利用経路や運用上の制約を示す。
代表的な入力・応答・エラー・権限を比較し、採用した API や責務分担の理由を残す。
別の機能追加や設定だけで対応しない理由が判断に影響したなら書く。

### 互換性と展開

影響するものだけを選び、新旧の組み合わせを表にする。

- クライアント / サーバー、送信側 / 受信側、writer / reader、ノード間のプロトコル。
- データ・schema・設定の既定値、既存データ、既存アカウント、外部利用者。
- 新旧混在中の読み書き、拒否・無視・変換の挙動、非対応バージョンへの対処。

ロールアウトには、投入順序、移行やバックフィル、有効化条件、確認する指標・ログ・操作を記載する。
段階投入をするなら、対象範囲、次段階へ進む条件、停止条件、無効化・切り戻し方法を書く。
単一の投入で足りるなら、その根拠を説明する。
実装のデプロイ、新機能の有効化、データ移行を同じ出来事として扱わない。

永続化済みの新形式を旧版が読めない場合など、rollback が成立しない条件を明示する。
その場合は、書き込み停止、前進修復、バックアップからの復旧など、採用する手段と前提を記載する。
未決定の展開条件を具体的な数値や手順で埋めない。

### 設計判断と検証

契約や責務を長期的に変える判断は ADR の要否を確認する。
新機能の正常系だけでなく、既存経路、混在、移行、無効化のうち必要な検証を示す。
実施済みの検証と、リリース時に実施する確認を分ける。

## Perf

### なぜ改善するか

遅延、処理量、CPU、メモリ、I/O、コストなど、利用者や運用に効く問題を具体化する。
プロファイルや実測で確認したボトルネックと、改善を狙う仕組みを対応させる。
キャッシュ、並列化、データ構造変更などを採る理由と、別案を採らない制約を説明する。

### 比較の条件と結果

同じ条件の Before / After を示し、条件を揃えられない場合は比較の限界を明記する。

- base / head のリビジョン、ビルド設定、実行コマンド、計測データの場所。
- CPU・メモリ等の環境、データ量・分布、並列数、キャッシュの cold / warm、測定範囲。
- ウォームアップ、試行回数、集計方法、ばらつき。指標に応じて中央値、p95 / p99、処理量など。
- 絶対値、単位、相対変化を併記。速度向上・レイテンシ低下など、数値の向きを区別する。

一つの条件の最良値だけで一般化しない。
未計測なら「改善見込み」とし、計測計画や未計測の理由を示す。結果欄を架空の数字で埋めない。
microbenchmark の改善を E2E や本番性能の改善と同一視しない。

### メモリフットプリントの指標

「メモリ使用量」だけでまとめず、**RSS と Physical Memory Usage を別の指標として記録する**。
Physical Memory Usage という表示名だけでは計上範囲が分からないため、
OS・ツール・API / カウンタ名まで対応付ける。

| 指標 | 記載する定義・測定元 |
|---|---|
| RSS | 常駐メモリの指標。`VmRSS` 等の取得元と、現在値か最大値かを明記する |
| Physical Memory Usage | ツール上の定義とカウンタ名を明記し、RSS とは分ける |

Linux の `/proc/PID/status` の `VmRSS` は anonymous・file・shared memory の常駐分から構成される。
取得方法による精度差もあるため、`VmRSS` と `smaps` の値を説明なく切り替えない。
[Linux の proc ドキュメント](https://docs.kernel.org/filesystems/proc.html)

macOS の physical footprint を使うなら、`proc_pid_rusage` の
`ri_phys_footprint` など取得元を記載する。memory footprint は圧縮・swap された
dirty memory の計上を含み、resident size とは一致しない。
physical footprintを「現在RAMに常駐するバイト数」と読み替えない。
[Apple の説明](https://developer.apple.com/videos/play/wwdc2022/10106/)と
[resident size / physical footprint の取得実装](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/bsd_kern.c)を参照する。

Before / After は同じカウンタ・対象範囲・単位・測定区間で比較する。
単一プロセス、子プロセス合算、コンテナ、ホスト全体を区別し、peak / 定常値、サンプリング間隔、負荷や圧縮・swapの条件を添える。
両指標の差が論点なら両方を示す。片方が未計測ならそう記載し、
RSS の減少だけで Physical Memory Usage の減少を主張しない。

### 引き受けるコスト

メモリ増加、CPU増加、tail latency、起動時間、複雑化、精度や整合性への影響を確認する。
「同じ契約を保って速くなる」のか、キャッシュの鮮度などの契約も変わるのかを書く。
悪化した条件や差がなかった条件も、判断に必要なら載せる。
新旧互換性や導入リスクがあれば、feature と同じ観点で展開方法を説明する。

## Refactor

今の構造で変更・検証・運用が難しい理由と、分割や依存関係の変更によって何が改善するかを書く。
責務やデータフローの Before / After と、維持する公開 API・状態・エラー・順序・性能上の契約を示す。
単に「挙動変更なし」と宣言せず、その判断と検証の根拠を残す。
移行途中の依存関係や後続 PR があれば、今回の変更範囲を明確にする。

## 運用・インフラ・依存更新

変更の契機（サポート期限、障害、脆弱性、運用上の負担等）と、現状維持の影響を書く。
設定値や依存バージョンの差分だけでなく、互換性、権限、接続経路、再起動・再配置への影響を示す。
依存更新なら upstream の変更内容と、このリポジトリで利用している機能への影響を確認する。
plan / dry-run の結果と実環境への適用・動作確認を区別する。
セキュリティを理由にする場合も、確認した問題と予防的な強化を分け、秘密情報を本文へ含めない。

## Docs・開発支援・テストのみ

誰がどこで迷う・見落とす・作業を繰り返すのかと、変更後に何を理解・実行できるかを書く。
説明・操作・判断の Before / After を示す。図が有効なら、実行時の構成図でなく利用手順や判断の流れを描く。
リンク、コマンド、例、スキルの発見経路など、実際に変えたものを検証する。
実行時の変更がなければ、互換性・ロールアウトはその理由を短く書けばよい。
テスト追加なら、何の契約の根拠を補うのかと、実際に実行された条件を示す。
