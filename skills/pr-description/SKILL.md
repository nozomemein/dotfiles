# PR Description

会話や実装過程を知らないレビュアーが、変更の必要性、採用案の妥当性、影響、検証の限界を判断できる本文を書く。
ファイルの変更一覧だけで終わらせず、**なぜ変えるのか、なぜこの方法なのか、なぜ他の方法を採らないのか**を説明する。
必要な根拠や図があるなら長くてよい。文字数や見出し数を揃えることは目的にしない。
WHY / WHY NOT は説明を考える軸として使い、PR のタイトル・見出し・図にそのままラベルとして出さない。
本文の言語はユーザーの指定やリポジトリの規約に合わせる。
日本語なら「背景と目的」「採用した方針と代替案」など、内容を表す自然な見出しにする。

## 書く前に集める根拠

- 最新の base / head と差分、既存の PR 本文を読む。最終的な変更範囲に合わせてタイトルと本文を更新する。
- 背景となる要求、Issue、障害ログ、再現条件、利用者への影響を確認する。
- 実装の前後、実行したテストと結果、ベンチマーク、関連 ADR を確認する。
- 関連 PR がある場合は、依存関係と、この PR 単体で導入される挙動を区別する。

根拠が不足していれば、分かる範囲で本文を作り、判断に影響する不明点を明記する。
数値、原因、比較案、検証結果、展開済みという事実を補って作らない。
観測事実、推定、提案、実装済み、検証済み、デプロイ済みを混同しない。

## 共通の説明

対象リポジトリに PR テンプレートがあれば出発点にし、次の問いへ答える。
テンプレートがなければ、変更に必要な説明だけで構成する。
冒頭で問題と変更後の動作を短く示し、背景と根拠を続ける。
問いをすべて独立した見出しにする必要はない。

| 問い | 本文に残す内容 |
|---|---|
| なぜやるのか（WHY） | 背景、困っている利用者や処理、現状維持の影響、達成したい状態。優先する理由があるならそれも書く |
| 何が変わるのか | 同じ入力・操作・障害条件での Before / After。挙動を維持する変更なら、維持する契約と変える内部構造 |
| なぜこの案か（WHY NOT） | 制約、採用理由、実際に検討した有力な代替案を採らない理由、引き受けるトレードオフ |
| 何が根拠か | 再現、テスト、計測の条件と結果、証拠へのリンク、未検証の範囲 |
| どう導入するか | 互換性、混在期間、移行・有効化の順序、確認条件、停止・切り戻し方法 |
| 判断をどこに残すか | ADR の新規作成・更新・既存参照・不要の判断と理由、関連資料 |

「なぜこの修正が問題を解くか」を因果でつなぐ。
例えば、検索入力に debounce を入れただけで、応答順序の逆転を防いだ、と説明してはいけない。
修正する原因・失敗経路と、残る原因や制約を示す。

WHY NOT のために架空の比較検討や弱い対案を増やさない。
明白な局所修正なら、現状維持が不適切な理由と、その範囲の修正で足りる根拠を短く書けばよい。

## 変更の種類に合わせる

[変更パターン別の観点](references/change-patterns.md)の該当する節を読む。
分類は排他的ではない。性能改善を伴う新機能なら、両方の観点を使う。

- **bugfix**: 発生条件、観測と推定、原因となる経路、修正前後の図、再現・回帰テスト。
- **feature / API・データ形式の変更**: 利用者の Before / After、旧版との互換性、混在と展開順、移行・切り戻し。
- **perf**: ボトルネック、同じ条件でのベンチマーク、再現手順、改善量とコスト・回帰。
  メモリは RSS と Physical Memory Usage を区別する。
- **refactor / 運用・依存更新 / docs・開発支援**: 変える構造や手順、維持する契約、変更固有の検証。

複雑な変更では、概要で問題と結果をつかめるようにし、本文で判断に必要な詳細を説明する。
大量のログや補助データはリンクや `<details>` に分けてもよいが、根拠・リスク・未検証事項を隠さない。
小さな文言修正まで、空の節や「該当なし」を大量に並べない。

## Mermaid と比較表を積極的に使う

時間順序、複数コンポーネント、状態遷移、失敗経路、互換性の混在が説明の中心なら、図を優先して検討する。
複数枚使ってよい。Before / After で参加者・用語・比較条件を揃え、変わる矢印・分岐・境界を示す。

| 説明したいこと | 向いている表現 |
|---|---|
| 通信、再試行、期限、非同期処理の順序 | `sequenceDiagram` |
| 処理経路、責務の移動、失敗時の分岐 | `flowchart` |
| 状態と遷移条件 | `stateDiagram-v2` |
| 新旧バージョンの組み合わせ、設定値、性能指標 | 比較表。数値の傾向にはグラフを併用 |
| UIや操作の変化 | 同じ操作条件のスクリーンショットや操作フロー |

図の前後で、読み取ってほしい変更点と、その変更が効く理由を文章でも説明する。
概念図・推定の経路・未実装の展開案は、そのことを図の近くに明記する。
失敗や通知が論点なら正常系だけを描かない。
Before / After の根拠を確認し、図とコード、数値、本文の対応を点検する。
Mermaid の表示を確認できない場合は、表示確認済みと記載しない。

図の書き出しに迷う場合だけ、[図と比較表の例](references/diagrams.md)を参照する。
例の値・原因・採用案を実際の PR の事実として流用しない。

## ADR とロールアウトの判断

責務境界、永続データ形式、プロトコル、整合性・可用性、セキュリティ境界、主要な技術選定など、
後続の変更にも効く判断は、対象リポジトリの ADR や設計記録の新規作成・更新・既存参照を検討する。
軽微な修正まで新規 ADR を必須にしない。要否が論点になる変更では、不要と判断した理由も短く残す。
未判断・未作成なら完了扱いにせず、何を決める必要があるかを書く。
ADR へリンクしても、今回の判断の要約と採用理由は PR 本文に残す。
ADR 自体を書く場合は、対象リポジトリの文書規約・テンプレートがあれば従う。
ADR の仕組みがなければ、継続的に参照する設計文書など、既存の記録先に合わせる。

新機能や互換性に影響する変更には、適用・有効化・移行の計画を含める。
段階投入や feature flag は必要な場合に使い、すべての PR に機械的に要求しない。
旧版に戻せないデータ変換などは、その境界と以後の復旧方法を書く。
文書だけの変更など実行時の影響がなければ、その理由とともに短く説明する。
展開計画を書くことは、実際のデプロイやマージを実施する許可ではない。

## 仕上げと反映

1. 背景から変更・根拠・導入方法へ、会話を読まずに追えるか確認する。
2. 実測と期待、局所テストと E2E、本番確認、未実施・失敗・スキップを区別する。
3. 代替案、図、計測値、ADR の状態が一次資料と一致するか点検する。
4. テンプレートの未使用節や説明用コメントを整理し、リポジトリの言語・Markdown 規約に合わせる。
5. ユーザーが PR 作成・本文更新を依頼していれば反映し、保存された本文を再取得して確認する。原稿作成やレビューだけの依頼なら本文または指摘を返す。

本文更新時は、既存の根拠リンク、関連 Issue、リポジトリの自動処理が読むマーカーを確認し、必要なものを保持する。
適用理由がなくなったマーカーは残さない。
根拠リンクは PR の読者が参照できるものを使う。個人のローカルパスや閲覧できない資料だけを根拠にしない。
公開 PR では、内部の組織名・顧客名・ホスト名・識別子や非公開資料の URL を転載せず、
説明に必要な内容を公開可能な範囲で要約する。架空の例は例と明記し、実測や実際の障害と混同しない。
この skill はレビュー依頼、他サービスへの通知、マージ、デプロイを自動で行わない。
