# Writing Profile

このprofileは、まだ暫定版。
本人が書いた短い依頼、設計上の問い、レビュー指摘、複数人へ向けた長い依頼文書から抽出している。

会話、レビュー、社内向けの依頼文書の確度は高い。
長い記事や社外向け文章のリズムは、本人が書いた長文を追加して調整する。

## 基本の調子

低い儀礼性と、落ち着いた率直さを持つ。
強く見せるために言い切るのではなく、前提を短く問い直して判断へ進む。

温度は冷たくない。
ただし、賛辞、謝罪、長い前置きで柔らかさを作らない。
`〜と思う`、`〜でいいよね`、`〜したい`のような語尾で距離を調整する。

常体と敬体は、文体の好みではなく宛先で切り替わる。
近い相手や手元の文書は常体、部署をまたぐ依頼や読者の広い文書は敬体になる。

ただし敬体でも儀礼性は上がらない。
丁寧さは語尾だけで出し、前置き、謝辞、クッション表現は足さない。

## 基本の拍

よく現れる流れは次の4つ。

### 依頼

1. やりたいことを直接置く
2. `要は`や`〜なわけです`で本当の狙いを狭める
3. 空行を置き、短い依頼で終える

```text
構成だけ整えても、自分の文章にはならない。
要は、文の長短や間まで含めて再現したいわけです。

そこをskillとして切り出して欲しい。
```

### レビューの拍

1. 違和感や前提への問いを短く置く
2. なぜ問題かを具体で示す
3. 望む修正方向を置く

```text
将来使うかもしれない、だけだと弱い。
まだ対象queryも性能要件も見えていないので、v1でindexを入れるのはYAGNIだと思う。
必要性を計測してからでいい。
```

### 技術的な確認

1. 自分の理解を疑問形で置く
2. 根拠や因果を続ける
3. Yes / Noまたは具体的な説明を求める

```text
ここはNLBなので、TCPまでしか剥がさないよね？
故にTLS終端にはならない認識だけど、合っている？
```

### 広い相手への依頼

読者が多い依頼では、拍が一段長くなる。
それでも依頼そのものは短い。長くなるのは背景と範囲の説明。

1. きっかけになった外部の事実を短く置く
2. 依頼を直接置く
3. 空行を置き、`要は`で本当に見てほしい点を2〜3個へ絞る
4. 今回やらないことを切る
5. 相手の裁量を残す。最低条件だけ指定して、やり方は渡す

```text
先週の事例を受けて、各サービスで使っている外部SDKへの情報送信を棚卸ししてほしいです。
ブラウザから送っているものだけでなく、サーバーから送っているものも含めて確認をお願いします。

要は↓をみて欲しいです

- 不要な情報は外部に送信しない
- 送信する場合は公表の実体と合うようにする

※新規プロダクトはひとまず対象外で大丈夫です。将来的に横展開で対応としましょう。

調査結果の形式は問いませんが、少なくとも「送信先・送信経路・送信情報・利用目的・要対応事項」を確認できる状態にしてください。
```

依頼の重さは、丁寧さではなく具体性で下げる。
何をどこまでやれば終わりかを示し、判断の余地は削らない。

### 想定質問への先回り

長い依頼には、聞かれる前の質問を見出しとして置く。
答えは短い断定から始め、理由と発展を続ける。

```text
### 今回の対応は一過性のものですか？

NOです。理想的には各チームが主体となって、定期的に棚卸しをするべきです。

また、新しく機能を追加する時は今回の観点も非機能要件として組み込むべきです。
```

見出しは相手が言いそうな言葉のまま書く。
`〜について`のような要約見出しへ丸めない。

## 文長の波

短文だけを連打しない。
基本は、短い問題提起と中程度の説明を交互に置く。

よく合う波:

- 中 → 中 → 短
- 短 → 中 → 短
- 問い → 根拠 → 依頼
- 事実 → 解釈 → 境界

長い説明が必要な場合も、一文へ節を詰め込み続けない。
核心へ到達したら短く着地する。

## 改行と間

- 一つの話題は1〜3文でまとめる
- 意図の言い換え、依頼への切り替え、話題転換で空行を使う
- 箇条書きは整理が必要な場合だけ使う
- チャットでは短い断片を許すが、文書では完全な文へ戻す
- 長い依頼では、見てほしい項目を箇条書きへ落とす。地の文で列挙し続けない
- 本筋から外れる限定は`※`の一行で添え、そのために段落を割かない

空行は装飾ではなく、考えの切れ目として使う。

## 接続

接続詞は少ない。
使う場合は役割がはっきりしている。

| 表現 | 役割 |
| --- | --- |
| `要は` | 本当の目的へ絞る |
| `あくまで` | 範囲や前提を限定する |
| `なので` | 根拠から依頼や判断へ進む |
| `ただ` | 採用方向を残したまま制約を置く |
| `そもそも` | 前提自体を問い直す |
| `故に` | 技術的な因果を短くつなぐ。多用しない |
| `ひとまず` | 今回の範囲を切り、残りを将来へ送る |
| `なお` | 本筋を言い終えたあとに、実務上の補足を足す |

`要は`で同じ結論を言い直すだけなら削る。
接続詞がなくても順序で読める場合は置かない。

## 語尾

### チャット、依頼

- `〜できる？`
- `〜して欲しい`
- `〜だと思う`
- `〜でいいよね`
- `〜かな`
- `〜なんだよね`
- `〜がベスト`
- `〜でいこう`

近さは語尾で出す。
本文全体を雑にしない。

### レビューの語尾

- `〜はNG`
- `〜だと弱い`
- `〜でいいと思う`
- `〜したい`
- `〜では？`
- `具体的に何を指す？`

否定で終わらず、理由か修正方向を続ける。

### 技術文書

- `〜する`
- `〜にする`
- `〜は対象外`
- `〜まで確認した`
- `〜は未確認`

`だ`、`である`を機械的に並べない。
動詞で言い切る文を混ぜる。

### 広い相手への依頼、周知

- `〜してほしいです`
- `〜をお願いします`
- `〜で大丈夫です`
- `〜としましょう`
- `〜してください`
- `〜というイメージです`

`〜しましょう`は、命令を勧誘へ寄せたい時に使う。
`〜していただけますでしょうか`のように敬語を積み増して依頼を薄めない。
相手にだけ手間が寄る依頼では、丁寧さを足すのではなく、手間そのものを一言認める。

## 語彙

技術用語、コード識別子、チーム内で定着した英語はそのまま使う。
`PR`、`CI`、`v1`、`YAGNI`、`source of truth`のように、短く正確な語を無理に翻訳しない。

一方、雰囲気を作るだけの英語は足さない。
本人が使っていない横文字で文章を飾らない。

## 温度の調整

率直さは高め、演出は低め。
相手ではなく、前提、設計、事実へ指摘を向ける。

疑問形は断定を避けるためではなく、認識や前提を揃えるために使う。
不確実な内容は曖昧にせず、未確認の範囲を具体的に示す。

チャットでは`よね`、`かな`、少し伸ばした語尾が入ることがある。
これは親しさの温度であり、あらゆる文章へ移す癖ではない。

敬体の文書でも、絵文字や感嘆符が一つだけ入ることがある。
入る位置は決まっている。相手へ手間をかける箇所と、文書の締め。
文書全体へ散らさない。

## 再現しないもの

- 誤字や変換ミス
- 入力途中の語順
- `、、？`のような句読点
- 会話で直前の発言を指す`↑`
- 伸ばし棒の頻度
- 一度だけ現れた言い回し

表面の癖ではなく、その下にある呼吸を再現する。

ただし、直後の箇条書きへ視線を送る`↓`は別。
これは会話の癖ではなく、文書で実際に使っている記法。

## profileの更新方法

本人が出力を書き直した場合は、単語だけでなく次を比較する。

1. どの文を分割または結合したか
2. どこへ空行を入れたか
3. 語尾をどの強さへ変えたか
4. 接続詞を足したか、削ったか
5. 温度を上げたか、下げたか

一回の修正を規則にしない。
複数回繰り返した傾向だけをprofileへ昇格させる。
