# Write Plan

実装前に採用方針を固め、判断理由・トレードオフ・却下した選択肢を残すための Markdown プランを作成するスキル。

プランは README や設計書ではない。「なぜこの方針を採ったか」「何は今回やらないか」を残すのが目的。

---

## 1. 出力モードを先に決める

プランには 2 モードある。**着手前にどちらで書くか決め、プラン冒頭に 1 行で明記する。** 選ぶモードで必須節と作業手順の範囲が変わる。

| モード | 想定用途 | 必須節の違い |
|---|---|---|
| **実装プラン** | 実装着手が視野に入る。コード変更 + PR までを見通す | `9. PR 分割案` と `11. 作業の進め方` を必須で書く |
| **設計 / 調査プラン** | 採用方針・調査項目・未解決論点が主。実装着手はまだ視野に入らない | PR 分割 / worktree / Draft PR 節は書かない or 「未定」とのみ記す |

迷ったら実装モード寄りで書く。ただし実装範囲が未確定なのに PR 分割を捏造しない。

---

## 2. 事前調査フェーズ（必ず先に行う、かつ並列で）

書き始める前に、以下を必ず確認する。推測で埋めると、既存コードと整合しないプランになる。

**重要**: 調査は可能な限り並列化する。逐次に Read / Grep を積み重ねると時間と context の両方を食う。

### 2-1. 並列化の原則

以下は独立しているので、利用可能な場合は同一ターンでまとめて調査する:

- 複数ファイルの Read
- 複数パターンの Grep / Glob
- 複数トピックのサブエージェント調査（Explore agent など）

調査範囲が広いときは、**最初の 1 ターンでサブエージェントを複数同時に spawn する** のが既定。サブエージェントは結果を要約して返すので main context の消費も抑えられる。

サブエージェント機能が利用できない環境では、Read / Grep をまとめ打ちして同等の粒度で調査する。

悪い例: `Read → Read → Grep → Read → ...` と逐次に積む。
良い例: 独立した調査トピックを並列サブエージェントに振り、結果を受け取ってから次の判断へ進む。

### 2-2. 対象コード / docs を読む

ユーザーが指示した対象パスについて:

- 現行実装の責務 / クラス構造 / CLI / config / API の形を確認する
- 既存 README / design doc / ADR を読み、前提となる用語を理解する
- 範囲が広ければサブエージェントを複数並列で spawn する（例: 「runtime 側の責務調査」「CLI 側の責務調査」「docs 側の用語整理」を別エージェントに振る）

### 2-3. 類似する既存プランを 1〜2 本読む

同じ保存先に既存プランがあれば、必ず 1 本は通読する。目的:

- 節構成 / 見出しの粒度 / 文体を合わせる
- プロジェクト固有の用語・スコープ語彙を踏襲する
- 重複・矛盾する決定が過去プランにないか確認する

類似プランの読解と対象コードの調査は独立なので、これも **並列** で行う。

### 2-4. 判断に必要な情報が不足していたら質問する

特に以下は推測で埋めない:

- プロジェクト固有の用語定義
- 対象 module / component の境界
- production / CI / dev の運用差
- 他プランとの依存関係
- 並列実装可能な範囲（競合するファイルがないか）

---

## 3. 保存先とファイル名

### 3-1. 保存先

決定順:

1. ユーザーが明示したパスがあればそれを使う
2. 明示がなければ、現在のリポジトリ内で既存の plan dir（`plans/` / `docs/plans/` / `doc/plans/` など）を探索し、見つかれば慣例に寄せる
3. それでも見つからない場合のみユーザーに確認する

即質問で止まらず、まず既存慣例を探す。

### 3-2. ファイル名規則

ケバブケース + `-plan.md` サフィックスを既定とする。

形式: `<context>-<feature>-plan.md`

例:

- `<subsystem>-<feature>-plan.md`
- `<component>-implementation-plan.md`
- `<area>-remaining-work-plan.md`

既存プランの命名があればそれを踏襲する。

## 4. プランのテンプレ構造

以下の **12 節（0〜11）** を既定とする。内容が薄い節は省略してよい。

- `0. サマリ`
- `2. 目的`
- `3. 非目的`
- `10. 判断`

- `9. PR 分割案`

## 5. 文体ルール

### 5-1. 言語と文体

- 本文は **日本語を基本** とする。既存の固有名詞、コード識別子、コマンド名、確立した技術用語は英語のままでよい。
- 常態（〜である、〜する、〜にする）で書く。敬体（〜です、〜ます）は使わない。
- 結論の言い換え（「要するに、〜」「つまり、〜」）は **`0. サマリ` と `10. 判断` の要所に限って** 使う。他の節で多用すると冗長になる。

### 5-2. 採用方針は番号付き箇条書き

`0. サマリ` の「採用方針は以下。」の下は必ず番号付きリストにする。裸段落では書かない。

### 5-3. スコープを時間軸で切る

以下の語彙を活用する:

- 「初期スコープ」「第一段階」「今回は〜に絞る」
- 「〜は後続実装に切り分ける」「将来対応とする」
- 「将来 〜 を正規サポートするなら、別途 〜 を入れる」

既存プランで `phase 1` / `Future Impl` 等の英語語彙が確立していれば、それに合わせる。

### 5-4. 非目的を明示する

`3. 非目的` は scope creep 予防として必ず書く。以下が典型:

- 本番既定化（production での mandatory default 化）
- 他 command / 他サブシステムの同時拡張
- 並列実行 / 分散実行
- 別レイヤ（transport / platform）への機能追加

### 5-5. コード例の言語タグ

- 言語ごとの正式なタグを使う（`ruby`, `rust`, `go`, `python`, `ts`, `bash` など）
- 出力例 / 疑似コード / ディレクトリツリー: `text`
- 設定ファイル / SQL: それぞれの言語タグ

### 5-6. 表を効果的に使う

- 残作業サマリ / 優先度 / 状態一覧は表で書く
- 単なる箇条書きで十分なものは表にしない

### 5-7. 「判断」節で最後に要点を打つ

`10. 判断` は読み手が最後に受け取る結論。以下を含める:

- 採るべき方針の再確認
- 優先度（高い / 次の一手として自然 など）
- 「まずは 〜 に絞って入れ、〜 は後続に切り出すのがよい」のような段階論

## 6. PR 分割案の書き方（実装プランのみ）

### 6-1. 並列実装を最優先で検討する

PR 分割の第一の軸は「並列に作業できるか」。逐次依存よりも並列可能な切り方を優先する。

以下を明示する:

- **各 PR の依存関係**（「依存: なし」「依存: PR1」など）
- **並列作業の可否**（「PR1 と PR2 は変更ファイルが分離しているので並列可」）
- **直列にせざるを得ない箇所の理由**（共有 interface 変更、schema 変更など）

### 6-2. 切り方の既定パターン

- 1 PR で済むなら「単一 PR で十分」と明言する
- 分けるなら **runtime / module → CLI / API → E2E** の順が典型
- **docs / README / ADR は原則としてその変更を生んだ PR に同梱** する（単独 docs PR は作らないのが既定）
- ファイル境界が切れている機能は並列 PR として切る

### 6-3. PR ごとに書く項目

- 何が入り、何は入らないか
- 依存関係（なし / PR X / 外部依存）
- 並列可否
- 想定レビュー観点

### 6-4. docs 更新の扱い

- 原則: コード変更を入れた PR に対応する docs / README / ADR 更新を同梱する
- 例外: 複数 PR にまたがる **横断的な docs 整理** のみ、別 PR として切り出してよい
- 別 PR に切り出す場合でも、`9. PR 分割案` に **理由と依存関係** を必ず書く

---

## 7. 作業の進め方（プラン内 `11.` 節の中身 / 実装プランのみ）

プランを読んだ人・実装する人（次のセッションの Claude 含む）が即作業に入れるよう、以下を明記する。

### 7-1. git worktree の使用は必須

**すべての作業は git worktree 上で行う**。main ブランチ直下で作業してはいけない。

典型的なディレクトリ配置を書く:

```bash
# base repo: ~/dev/<project>
# worktree root: ~/dev/<project>-wt
git worktree add ~/dev/<project>-wt/<feature-branch> -b <feature-branch>
```

PR を並列に回すなら **PR ごとに worktree を切る**。

```text
~/dev/<project>-wt/
  feature/pr1-<name>/
  feature/pr2-<name>/
  feature/pr3-<name>/
```

並列で開発している別 PR の worktree を壊さないよう、各 worktree は自分のブランチに閉じる。

### 7-2. 並列実装の割り当て

PR 分割案の依存関係から、**どの PR が同時並行で進められるか** を明記する。

例:

```text
PR1 (runtime) と PR2 (CLI) は並列実装可。
PR3 (E2E) は PR1 / PR2 のマージ or feature 完成を待つ。
```

Claude Code で並列に回すなら、**それぞれ別 worktree で別セッション** を立ち上げるのが既定。

### 7-3. docs / ADR の更新は作業範囲に含める

各 PR の作業範囲には、該当する docs / README / ADR の更新を **原則含める**。コードだけ入って doc が stale になるのは避ける。

- 仕様変更: 対応する design doc / README / user guide を同じ PR で更新
- アーキテクチャ判断を伴う場合: ADR が運用されていれば、新規 ADR を起票するか既存 ADR を修正する
- ADR が存在しないプロジェクトでは、プラン内の `10. 判断` が同等の役割を果たす旨を明記する

横断的な docs 整理を別 PR に切り出す場合は、`9. PR 分割案` に理由と依存関係を書く（`6-4` 参照）。

### 7-4. ゴールは Draft PR まで

各 PR の作業単位の「ひとまずのゴール」は **Draft PR 作成まで** とする。

- 実装 + 自動テスト green
- 該当する docs / README / ADR の更新込み
- セルフレビュー済み
- PR 本文に目的 / 非目的 / テスト範囲 / 依存 PR / 更新した docs を書く
- `gh pr create --draft` で Draft として上げる
- ここで作業を止め、**ヒューマンレビューに渡す**

Ready for Review 化・マージはヒューマン判断。Claude は Draft PR 以降は明示的な指示があるまで触らない。

### 7-5. 実装中の並列化

PR 内部の作業でも、**変更対象ファイルが分離している場合に限り** ツール呼び出しを並列化する（独立ファイルの Edit、独立 test の実行など）。同じファイルの連続 Edit や依存のある変更は直列で行う。

---

## 8. 実行手順

1. ユーザーから「何について」「どのスコープで」プランを書くか受け取る
2. **出力モードを決める**（実装プラン / 設計・調査プラン）
3. 保存先を決める（明示あり → そのパス / なければ既存 plan dir を探索 / それでも見つからなければ確認）
4. **事前調査フェーズ** を実行する
   - サブエージェントを複数並列で spawn、Read / Grep も並列
   - 類似プランを 1〜2 本読んで構造と用語を揃える
   - 不明点があればユーザーに質問する
5. 節構成をドラフトする（0〜11 のどれを採用するか、モードに応じて決める）
6. **採用方針** を先に固める。これが決まらない状態で詳細を書かない
7. 各節を埋める。文体ルール（常態 / 「要するに」は要所限定 / 箇条書き形式）を守る
8. 実装モードなら `9. PR 分割案` で並列実装可否を明示する
9. `10. 判断` を書き、採用理由と後続への切り分けを明記する
10. 実装モードなら `11. 作業の進め方` で git worktree 配置と Draft PR ゴールを明記する
11. `<context>-<feature>-plan.md` の命名で保存する
12. 保存先 / ファイル名 / 概略をユーザーに報告する

---

## 9. やってはいけないこと

- 調査せずに推測だけで埋める
- 調査を逐次で積む（並列化を怠る）
- プロジェクト固有の用語を勝手に再定義する（既存プランに定義があれば踏襲）
- 敬体で書く
- 「要するに / つまり」を各節で多用して冗長にする
- 後続に回すべき機能を初期スコープの目的に混ぜる
- `3. 非目的` / `10. 判断` を省略する
- 実装プランなのに `9. PR 分割案` / `11. 作業の進め方` を省略する
- 設計・調査プランで無理に PR 分割や worktree 指示を捏造する
- docs / README / ADR 更新を **無根拠に** 後回しにする
- docs を別 PR に切り出す場合に、理由と依存関係を書かない
- Draft PR を超えて勝手に Ready for Review / マージを進める
- README / design doc と重複するだけのドキュメントを書く（プランは判断理由を残すもの）
