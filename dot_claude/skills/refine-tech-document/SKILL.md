# Refine Tech Document

技術文書の推敲を行うスキル。**推敲は基本的に文書を短くする**。長くする方向に動いたら、たいてい間違っている。

主旨は次の 4 つに集約される:

1. **論理の骨格が通っているか** (段落間の繋がり・主張と例の対応)
2. **why / why-not が示されているか** (判断・選択・トレードオフの理由)
3. **読者の負荷を不要に上げていないか** (固有名詞・抽象語・冗長)
4. **LLM っぽい空虚な表現を駆逐したか**

## 1. 動作モードを先に決める

着手前にモードを 1 行で宣言する。モードによって出力形式と作業範囲が変わる。

| モード | 目的 | 想定入力 |
|---|---|---|
| **全面推敲** | 草稿を全面的に書き直す | 構成・表現ともに荒い草稿 |
| **段落ごと推敲** | 構成は残し、節 / 段落単位で直す | 構成は OK、表現や論理が雑 |
| **ギャップ検出のみ** | 推敲はせず、論理の穴・段落の繋がりの欠落だけ指摘 | 自分で直したい場合 |
| **軽推敲** | 表記揺れ・冗長・LLM っぽさだけ落とす | 最終仕上げ |

迷ったら **ギャップ検出のみ** から始める。論理の骨格が壊れている文書を表現だけ磨いても無意味。

---

## 2. 事前読解フェーズ

書き直し / 指摘の前に必ず行う。

- 文書を 1 回通読し、**章 / 節構造を箇条書きでメモ**する
- 想定読者 (誰が読む) / 目的 (何のため) / 置かれる場所 (公開ブログ・社内 Wiki・PR 本文 など) を特定
- 同種の周辺ドキュメントがあれば文体・用語を合わせる
- 推敲する前に、**論理の骨格が成立しているか**を先に判定する。骨格が壊れているなら表現磨きはやらない

---

## 3. 推敲の観点

各推敲時に以下を機械的にチェックする。順番は重要度順。

### 3-1. 論理の通り方

- 段落の先頭で、前段との論理関係 (順接・対比・補足・反例) が読める
- 1 段落 1 トピックに絞る
- 結論を 2 度繰り返さない (反論処理が終わった後に 1 度だけ置く)
- 例 / 反例 / 譲歩のあと、必ず論を進める (逆接で終わらない)
- 主張が、挙げた例で本当に支えられているか
- 因果を主張するときは「なぜそうなるか」を 1 文で示す
- 異なるものを「同じ」とまとめない / 複数要因を単一原因に還元しない
- 山場で効かせたい情報を、手前の段落で先出ししない

### 3-1-b. why / why-not を書く (★ 技術文書で特に重要)

技術文書は「何をした (what)」「どうやった (how)」だけでなく、**「なぜそうしたか (why) / なぜそうしなかったか (why-not)」** を書く。これがない文書は、後から読んだ人が判断を再現できない。

チェック観点:

- 設計選択・技術選定・採用方針には、**採用した理由 (why)** が書かれているか
- 検討して却下した選択肢があれば、**却下理由 (why-not)** が書かれているか
- トレードオフ (何を取り、何を諦めたか) が明示されているか
- 「ベストプラクティスだから」「業界標準だから」だけで済ませていないか (それは why ではなく権威への参照)
- 制約条件 (時間 / 予算 / 既存システム / 組織事情) は判断理由として書かれているか

how だけが並ぶ文書、why だけが並ぶ文書はどちらも片肺。**判断の現場を再現できる粒度**で書く。

代表的な不足パターン:

- 「X を採用した」とだけ書き、Y / Z を検討したかが見えない
- 「A の方が良い」とだけ書き、A が良い**理由**が書かれていない
- 過去の経緯 (history) はあるが、現在の判断 (present decision) との繋がりが切れている

### 3-2. 段落ごとのギャップ検出

各段落について、次の 3 つを言えるかを確認する。

| 項目 | 内容 |
|---|---|
| 受ける | 前段落から何を引き継ぐか |
| 役割 | この段落が論証の中で果たす役割 |
| 渡す | 次段落に何を引き渡すか |

**書けない段落は「ギャップ」とみなす。** 修正は表現変更でなく、削除 / 順序入れ替え / コラム化 / 加筆など **構造で対応**する。

よくあるギャップ:

- 前段で導入していない語が、次段の主語に突然なる
- 引用や理論が、後続の主張を一切変えていない (空転)
- 例と主張で「問いの型」が違っている (主張は "なぜ" の話なのに、例は "どう" の話)
- 別話題が割り込む A-B-A 構造
- 術語が説明前に使われている (過早導入)

### 3-3. 可読性 / 整形

- **一文ごとに改行**、段落は空行で区切る
- コード・ログ・コマンドはコードブロック化
- 補足情報は脚注または別節に降ろす (本文を細らせる)
- 用語の初出は太字、以降の言及は「」
- ファイル名・関数名は **後で再参照されるときだけ**出す。装飾で出さない
- em ダッシュ・中黒・罫線で見出しを飾らない
- 見出しは「単一の自然な句」に統一する
- 英単語・固有名詞は **公式表記 (canonical form)** に従う。一般小文字や雑な綴りで書かない

#### 公式表記の例

| 誤った表記 | 正式表記 |
|---|---|
| github | **GitHub** |
| pull request | **Pull Request** (機能名として参照する場合) |
| javascript | **JavaScript** |
| typescript | **TypeScript** |
| nodejs / node.js | **Node.js** |
| postgresql | **PostgreSQL** |
| mysql | **MySQL** |
| docker | **Docker** |
| kubernetes | **Kubernetes** (略称は `k8s`) |
| openai | **OpenAI** |
| anthropic | **Anthropic** |

判定基準: **公式ドキュメント / 公式サイトでどう書かれているか**を一次資料とする。記憶で書かず、迷ったら公式を確認する。

### 3-4. 文体

- **常体 (だ・である) を基本**とする ★ 好みで切り替え可
- 個人視点を入れない (「私は」「個人的には」を避ける)
- 「弊社では」など自明な前置きは削る
- 読者を「あなた」と呼ばない。役割名 (開発者・運用者・レビュアー) を使う
- 命令調より「ここで X すると Y になる」のように現象として書く
- 術語を導入したらその語で通す。途中で曖昧語に後退しない

### 3-5. 表現の節度

- 強調 (太字) は 1 節につき 1〜2 箇所まで、論理の要所だけ
- 「重要なのは」「ポイントは」で主張を予告しない
- 修辞疑問・対句・決めゼリフを多用しない
- 比喩はひねらず、**平易な動詞**で言う
- 転回点を過剰に劇的化しない
- 短い決め台詞を独立段落にしない

### 3-6. 冗長性の排除

- 同じ主張を言い換えて繰り返さない
- 「要するに」「つまり」で締め直さない (主張は 1 度だけ)
- 接続と評価だけの文を置かない
- 読者が自力で補える中間段階を書かない
- メタな枠取り (「〜という発想である」「〜という観点が大事」) で紹介しない
- 著者立場の弁明を書かない (「これはあくまで一意見だが」など)

### 3-7. LLM っぽい表現の駆逐 ★ 最重要

以下は「何かを言っているように見えて何も言っていない」表現。**機械的に削除 or 言い換える**。代替が思いつかなければ **文ごと削る**判断を優先する。

| 類型 | 典型表現 |
|---|---|
| 予告・総括 | 「本章では〜を扱う」「本記事では〜について解説する」「要するに」「に他ならない」 |
| 姿勢の宣言 | 「正面から扱う」「真摯に向き合う」「丁寧に解説する」 |
| 空虚な形容 | 「不可欠」「核心的」「多角的」「包括的」「シームレスに」「強力な」「効率的な」 |
| 空虚な動詞 | 「掘り下げる」「言及する」「踏み込む」「迫る」 |
| 接続の型 | 「において」「の観点から」「の文脈で」「に関して」 |
| 根拠なき緩和 | 何の裏付けもない「かもしれない」「非常に」「とても」「ある意味」 |
| 演出 | 「実は」「驚くべきことに」「興味深いことに」 |
| 結論の押し付け | 「〜であろう」「言うまでもなく」「明らかである」 |
| 不自然なカタカナ語 | 「シームレス」「ホリスティック」「ロバスト」「スケーラブル」「アグリー」「キャッチアップ」「コンセンサス」「ステークホルダー」 (※下記参照) |
| 不要な英語混入 | 「robust な設計」「seamless に連携」「commit する」「review する」「deep dive する」「focus する」 |
| 冗長な並記 | 「リファクタリング (refactoring)」「永続化 (persistence)」など、片方で足りるのに両方書く |
| 曖昧な役割名詞 | 「owner」「operator」「manager」「handler」「ledger」「lease」「context」「state」(中身を特定しないまま使う場合。※下記参照) |

★ このリストは育てる前提。実運用で見つけたパターンを足していく。

#### 不自然なカタカナ語 / 英語混入の判定基準

機械的に駆逐していいわけではなく、技術用語として定着しているものは残す。判定は次の順で行う。

1. **業界で定着している術語か?** (例: `API` / `commit` / `pull request` / `Docker` / `kubectl`) → 残す
2. **日本語にぴったりの一語があるか?** → 日本語に置き換える
   - 「キャッチアップ」→「追いつく」「把握する」
   - 「アグリー」→「同意する」
   - 「コンセンサス」→「合意」
   - 「ステークホルダー」→「関係者」
   - 「ホリスティック」→「全体的」「総合的」
   - 「ロバスト」→「頑健」「壊れにくい」
   - 「シームレス」→ ほぼ常に削除可 (中身がない)
3. **コード識別子・固有名詞か?** (例: 関数名 `commitChanges`) → そのまま
4. **上記いずれでもなく、日本語の文脈に突然英語が混入** → 駆逐対象

特に **「英単語 + する / な / の」** の組み合わせ (commit する、robust な、seamless の) は、LLM 生成物の強いシグナル。日常会話で誰も言わない言い回しなら、書き言葉でも避ける。

判定に迷ったら「**この語を口頭で同僚に説明するときに自然に言うか?**」を基準にする。言わないなら書かない。

#### 曖昧な役割名詞の検出と修正

「owner」「operator」「handler」「manager」「ledger」「lease」「context」「state」「service」「component」「entity」など、**抽象的な役割を指す名詞**は、技術文書で頻出する一方で、しばしば中身を特定しないまま使われる。

これらは固有の技術用語として定着している場合 (例: Kubernetes Operator パターン / Raft の lease) は OK。問題は **「何の owner なのか」「何を operate するのか」が文章から復元できない**まま使われるケース。

検出ルール: 上記の語が出てきたら、**「of WHAT」「does WHAT」が直近の文 / 段落から具体的に読み取れるか**を確認する。

| 駆逐対象の例 | 修正の方向 |
|---|---|
| 「リクエストの owner が処理を行う」 | owner = 誰? → 「リクエストを発行したサービス」など特定 |
| 「context をハンドラに渡す」 | context = 何を含む? → 「リクエスト ID とユーザー ID を含む context」など内容を明示 |
| 「lease を取得して操作する」 | lease の対象・期限・解除条件は? → 「N 秒間有効な書き込みロック」など実体で書く |
| 「manager が再起動を制御する」 | manager = どのコンポーネント? → 具体名 (`SupervisorProcess` など) |

修正の基本方針: **抽象的役割名詞は、初出時に「何の / どんな」を補足する**。補足できないなら、その語を使わずに具体名で書く。

### 3-8. 読者への誠実さ

- 例が作為的に見えるなら、そう認める ("単純化のため X は省く" など)
- 根拠は著者の断定でなく、**読者経験 / 一般的事実 / 出典**に求める
- 未確認のことを、確認済みのように滑らかに書かない
- 推量表現に **根拠があるなら残す** (削って断定にしない)
- 検出・保証・解決を「必ず」できるかのように書かない

## 4. 出力形式

### 4-1. 全面推敲 / 段落ごと推敲

1. 推敲後の本文 (Markdown)
2. 末尾に **変更点ノート** を箇条書きで添える (★ 好みで省略可)
   - 削除した段落 / 文 → 削除理由
   - 大きく書き換えた箇所 → 何を残し何を捨てたか
   - 構造変更 (順序入れ替え・節の統合 / 分割)
3. **削除候補**は別枠で残し、判断を仰ぐ (勝手に消し切らない)

### 4-2. ギャップ検出のみ

```
## 段落 N: <段落の冒頭抜粋>
- 受ける: <前段との繋がり>
- 役割: <この段落の論証上の役割>
- 渡す: <次段へ何を渡すか>
- ギャップ: <検出した穴>
- 提案: <構造的修正 (削除 / 順序入替 / コラム化 / 加筆)>
```

### 4-3. 軽推敲

推敲後の本文のみ。ノート不要。差分が大きいときは diff 風に提示。

## 5. やってはいけないこと

- **推敲のたびに文書を長くする** (推敲は基本短くなる方向。長くなったら疑う)
- 書き手の **意図を確認せず主張を変える** (表現は直してよい、主張は確認する)
- 「これは LLM っぽい」とだけ言って **代替案を出さない**
- 1 段落の中だけ見て直す (前後関係を見ずに局所最適化)
- **文体の好みを根拠なく押し付ける** (★ 設定が常体ならそれに従う)
- **作為的に章立てを増やす** (見出し数 = 構造の良さではない)
- 自分の推敲で **新しい LLM っぽさ**を混入させる (空虚な接続詞・空虚な総括)

## 6. カスタマイズポイント

★ 付きの箇所はユーザーの好みで切り替える前提。プロジェクトや媒体ごとに上書きしてよい。

| 設定 | デフォルト | 切り替え候補 |
|---|---|---|
| 文体 | 常体 (だ・である) | 敬体 (です・ます) |
| 変更点ノート | 出す | 省く / 概要だけ |
| LLM っぽい表現リスト | §3-7 のリスト | 案件で追加 |
| デフォルトモード | ギャップ検出のみ | 全面推敲 / 軽推敲 |
| 出力言語 | 入力に従う | 強制 ja / en |
| Markdown 記法 | 標準 | 媒体に合わせ調整 (Zenn / Qiita / 社内 Wiki) |

## 7. ワークフロー要約

```
1. モード宣言 (1 行)
   ↓
2. 通読 → 構造メモ → 想定読者を確認
   ↓
3. 骨格判定: 論理の骨格が成立しているか?
   ├ NO  → ギャップ検出モードに切り替え、構造の指摘で止める
   └ YES → §3 の観点で推敲
   ↓
4. 推敲後、自分の出力をもう 1 度 §3-7 (LLMっぽさ) で再点検
   ↓
5. モードに応じた出力形式で提示
```
