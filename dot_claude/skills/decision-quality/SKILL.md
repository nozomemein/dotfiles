# Decision Quality と設計判断失敗パターン

出典: [kawasima / Decision Quality と設計判断失敗パターン](https://scrapbox.io/kawasima/Decision_Quality_%E3%81%A8%E8%A8%AD%E8%A8%88%E5%88%A4%E6%96%AD%E5%A4%B1%E6%95%97%E3%83%91%E3%82%BF%E3%83%BC%E3%83%B3)

## 中心命題

**全体の質は最も弱い要素で決まる。** 観測される失敗のほとんどは「Frame（支配軸）」と「Values（評価軸）」の取り違えで説明できる。AI エージェントは判断軸を持たないので、暗黙知に依存していた抑止が効かない。**自分がいまどのパターンに入っているかを人間側で自覚する**ためのチェックリスト。

## DQ の 6 要素

| 要素 | 中身 |
|---|---|
| Frame | 解くべき問題の枠組み（＝支配軸の選択） |
| Alternatives | 選択肢の幅 |
| Information | 情報の信頼性 |
| Values | 評価基準（＝評価軸） |
| Sound Reasoning | 論理的推論 |
| Commitment to Action | 実行へのコミット |

## 9 つの評価軸

判断時に「どの軸を支配軸にするか」を 1 つに絞り、残りは二次条件として最低水準を決める。

1. **目的適合性** — そもそも目的を満たすか
2. **制約適合性** — 機能・非機能要件、業務制約を満たすか
3. **実現可能性(技術)** — 技術的に成立するか
4. **実現可能性(組織)** — その組織のスキル・体制で運用・保守・進化させられるか
5. **品質影響** — 保守性・運用性・進化性・変更容易性などの -ility
6. **時間効果** — 短期 / 長期で別軸として扱う
7. **リスク・不確実性** — 不確実性の評価
8. **整合性** — 既存アーキテクチャ・規約との一致（記録手段としての ADR）
9. **合意可能性** — Commitment to Action（関係者が実行できるか）

## 支配軸の取り違え（典型）

- 障害対応なのに、長期的な理想設計を始める
- 基幹刷新なのに、短期実装容易性だけで選ぶ
- セキュリティ問題なのに、UX だけで判断する
- PoC なのに、本番運用品質を要求する
- 本番機能なのに、PoC の速度感で作る

## 16 の設計判断失敗パターン

各パターンは「症状 → 主に偏る軸 → AI が陥りやすい点」の三点で覚える。
軸の記法: `↑` 過大評価 / `↓` 過小評価 / `評価不能` 情報不足

### 1. 車輪の再発明
標準解があるのに独自実装に逸脱。`目的適合性↑ / 整合性↓ / 実現可能性(技術)↓ / 品質影響(保守性)↓`
AI: 「動く」が正道から外れる。「普通これは自作しない」は AI から出ない。

### 2. 牛刀をもって鶏を割く
規模・複雑度に対して過剰なアーキテクチャ。`目的適合性↑ / 時間効果(短期)↓ / 品質影響(運用性)↓ / 合意可能性↓`
AI: 文脈非依存で「ベストプラクティス」を持ち込む。

### 3. 身の丈に合わない設計
技術的に望ましいが運用組織のスキルを見ていない。`実現可能性(技術)↑ / 実現可能性(組織)↓ / 品質影響(運用性)↓ / リスク↓`
AI: 組織のスキル分布を知らない。指示に運用前提を書かないとベストプラクティス側に寄る。

### 4. 羹に懲りて膾を吹く
組織スキルを過小評価して技術的に劣る選択。`実現可能性(組織)↓ / 品質影響(進化性)↓ / 時間効果(長期)↓`
人間側の下方迎合パターン。「現実的判断」と見えるため自覚されにくい。

### 5. 場当たり対応
短期に通るので判断の手前で止まらない。`時間効果(短期)↑ / 整合性↓ / 品質影響↓ / 時間効果(長期)↓`
AI: 局所的に通るコードを高速に出す。ブレーキは人間しかかけられない。

### 6. 早合点 (execution hallucination)
`200 OK / テスト緑 / コマンド完走` を目的達成と混同。`目的適合性 評価不能 / 整合性↓ / リスク↓`
AI: 戻り値・終了コードを成功条件と等価に扱う癖がある。「成功した」は「コマンドが完走した」以上を意味しない。

### 7. 見切り発車
要求/作戦が定まらないまま実装着手。`目的適合性 評価不能 / 制約適合性 評価不能 / 時間効果(短期)↑ / 合意可能性↓`
AI: 動くものが早く出るので、仕様の空白を実装で埋めたと錯覚させる。

### 8. 早すぎる抽象化
変化点が 1 度も観測されていない段階で抽象化。`品質影響(変更容易性)↑ / 目的適合性↓ / 時間効果(短期)↓`
打ち手: Rule of Three（変化点 2 回以上で抽象化）。`flexibility / extensibility` の語が出たら危険信号。

### 9. 制約の後付け
権限・履歴・監査・冪等性・状態遷移を機能の後に足す。`制約適合性↓ / リスク↓ / 品質影響↓`
AI: 機能の見える形を先に出すので、制約が「追加実装」扱いになりやすい。新規設計ではデータモデル/ユースケースに最初から織り込む。

### 10. 過去への忖度
互換性要件の実利用者と保証範囲を確認しないまま、最大限保守的に複雑化。`制約適合性↑ / 目的適合性↓ / 品質影響(保守性)↓`
AI: 「既存テストを通したまま」と指示すると、テストの本来意図を疑わず**全部通す方向の最も複雑な解**を選ぶ。`保つ範囲 / 期限 / 廃止計画` を必ず明記。

### 11. 名ばかりの完了
受け入れ基準が判定可能な粒度に分解されていない。`合意可能性↓ / 目的適合性 評価不能`
例: 「正しく表示」「適切にログ出力」「現行と同等」。入力・状態・期待結果・例外条件まで分解してから着手。

### 12. 越境実装
責務の本来位置でないところに書く。`整合性↓ / 品質影響(保守性)↓ / リスク↓`
AI: 「どこに書くべきか」より「どこに書けば今動くか」に寄ることがある。

### 13. 郷に従わぬ正論
プロジェクトの既存規約を読まず、一般論で空白を埋める。`整合性↓ / 目的適合性↓ / 実現可能性(技術)↓`
AI: 「一般的 Web 開発」の知識で空白を埋める。既存コードを読みに行く動作を強制しない限り減らない。

### 14. 隣を見ない再実装 (Comprehension Debt)
似た役割の関数/クラスを既存に確認せず新規作成。`整合性↓ / 品質影響(保守性)↓ / 合意可能性↓`
AI: 指示箇所の周辺だけ読んで実装する傾向。`新規ファイルを作る前に既存を検索` を CLAUDE.md に明記すると頻度が下がる。

### 15. 砂上の依存 (package hallucination)
存在しないライブラリ/関数/引数を呼ぶ。`実現可能性(技術)↓ / リスク↓ / 制約適合性↓`
slopsquatting 攻撃のリスクあり。一次資料での存在確認 + 実行確認をセットで。`pip install` が通っただけで信用しない。

### 16. 取らぬ狸の拡張点
将来変化が口頭で語られているだけで、時期/責任者/便益が紐づかない段階で拡張点を作る。`時間効果(長期)↑ / 時間効果(短期)↓ / リスク↓`
「将来 ◯◯ するかも」の `◯◯` に責任者と時期がないなら却下。「早すぎる抽象化」との違い: あちらは変更容易性の過大評価、こちらは長期効果の過大評価。

## 使い方（セルフチェック手順）

提案・実装方針・PR を出す前、または AI の提案を採用するか迷ったときに以下を 30 秒で問う:

1. **支配軸は何か？** — いまの判断で最も重視している評価軸を 1 つに絞る
2. **本来の支配軸とズレていないか？** — 障害対応 / PoC / 本番 / セキュリティなど、Frame の取り違えがないか
3. **どのパターンに最も近いか？** — 上記 16 から該当しそうなものを 1〜2 個ピックアップ
4. **敢えてそのパターン側を選ぶ理由を言語化できるか？** — 軸のズレを自覚した上で選ぶなら、理由と期限を明示する。言語化できないなら別の選択肢を再検討
5. **二次条件の最低水準は？** — 支配軸以外の軸で「ここを下回ってはいけない」線を明示

## AI エージェントが特に陥りやすいパターン

- **6. 早合点** — 戻り値ベースの成功判定
- **10. 過去への忖度** — テストを通すために複雑解を選ぶ
- **13. 郷に従わぬ正論** — 既存規約を読まず一般論で書く
- **14. 隣を見ない再実装** — 既存ユーティリティを検索しない
- **15. 砂上の依存** — 実在しない API を呼ぶ

これらは指示の出し方で抑止できる。プロンプト/CLAUDE.md に「既存コードを読んでから書く」「業務的な成立条件で検証する」「一次資料で存在確認する」を明記する。

## 関連 skill

- `write-plan` の前段でこの skill を参照すると、計画段階で支配軸を明示できる
- `code-review` / `review` の前にセルフチェックとして使える
- `codex` で設計相談を投げる際、プロンプトに「下記 16 パターンに該当しないか点検した上で提案して」を含めると Codex の出力が締まる
